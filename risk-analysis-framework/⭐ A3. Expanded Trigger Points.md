# ⭐ A3.Expanded Trigger Points: Customer Support Lookup Failure

## A. Roster not synchronized with registration system

- Backend systems showed valid scheduled records, but the roster did not reflect the entity.
  
- No automated alert existed for the condition “record exists in backend but missing from roster.”
  
- Roster refresh or sync mechanism failed or lagged.
---
  
## B. Customer support failed to use ID lookup

- **No ID-first triage** — Support agents did not use the candidate ID as the primary lookup key.

- **Repeated problem descriptions** — Each transfer required the user to re-explain the issue, indicating no case context retention or ticket continuity.

- **Unnecessary transfers** — Calls were repeatedly routed without any diagnostic steps or ownership, reflecting gaps in triage governance.

- **Irrelevant questioning** — One agent asked for the physical location of the test center, showing a lack of understanding of the issue and no access to the correct systems.

- **No unified candidate profile** — Support agents lacked a single source of truth combining registration, scheduling, and backend activity data.

- **Knowledge base gap** — Agents did not know how to diagnose cross-system mismatches or what information was relevant.

- **Workflow fragmentation** — No clear routing logic, escalation criteria, or triage protocol existed, leading to inefficiency and confusion.

---


## C. On-site staff relied solely on roster

- **Assumed local list was authoritative** — Operational staff treated the local access list as the single source of truth and did not attempt ID-based verification until late in the process.

- **No multi-source validation checklist** — There was no procedure requiring staff to cross-check unique identifiers against registration records and backend scheduling systems.

- **Over-reliance on a single data source** — Dependence on one operational dataset created avoidable delays and escalations when discrepancies occurred.
